The problem

The business ran on seven separate tools, built at different times, that didn't share data with each other.

  • The same product was entered four times, once in each tool.
  • Google results were loaded by hand and eventually stopped being loaded, so the analysis had no data.
  • Campaigns could be created, but not managed afterwards.

The solution

A single application where the product is the center and everything else hangs from it. It's entered once and every module uses it.

  • Google data comes in on its own every day at 6 a.m.
  • Campaigns are created and managed from the same screen.
  • The AI reads the results and builds a report with what needs a decision today.

How it's built

Three separate layers. The screens never talk directly to Google or the AI: everything goes through the server, the only place that holds the keys.

The 10 modules

A module never reads another module's tables: it asks for the data through that module's own door. That way each one can change without breaking the rest.

The journey of one record

What happens, step by step, when someone creates a new product and clicks Save.

  1. 1

    The screen sends the form

    React sends the data to the server as JSON, along with the user's session.

  2. 2

    A single entry point

    Every request comes in through the same server file, which hands it to the route list.

  3. 3

    Checks before anything else

    Requests from other sites are blocked, and the server checks the session is valid and the user can edit products.

  4. 4

    The data is validated

    The Products module checks everything is right before saving.

  5. 5

    Saved safely

    Saving uses prepared statements, so nobody can inject malicious code into the database.

  6. 6

    Every record in its environment

    The product is tagged with the client it belongs to, so data never gets mixed.

  7. 7

    It's logged

    The audit log records who did what and when.

  8. 8

    Response to the screen

    The server returns the new product's ID and the screen opens its record.

Security

This system handles Google accounts and campaign money, so security was designed in from the start.

PasswordsStored with bcrypt hashing, never as plain text.
Sensitive dataEncrypted with AES-256-GCM.
Google and AI keysOnly on the server, outside the public folder and outside Git.
Login attemptsRate limit per IP and Cloudflare bot check.
Forged requests from other sitesBlocked before they reach the logic (CSRF protection).
PermissionsPer module: no access, view only or edit.
Client separationEvery business table knows which client each row belongs to.

Quality and delivery

  • 227 automated test files: PHPUnit on the server and Vitest on the screens.
  • Google connections are tested with simulated responses, without touching real accounts.
  • Every part has a written, approved design before it's built.
  • Every bug is documented with its cause, its fix and how to check it.
  • Deployment over SSH, comparing every file with the repository.
  • Data from the old tools migrated with scripts that never create duplicates.

What I'd do next

  • A dedicated server as users grow; shared hosting has limits.
  • Automatic alerts when something fails, instead of checking the dashboard.
